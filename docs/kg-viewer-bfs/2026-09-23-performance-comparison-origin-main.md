# KG Viewer 3000 节点性能对比

## 结论

以当前远端主干 `origin/main`（`6a36da8`）为基线，和优化工作树 `optimize/kg-viewer-3000`（`e202613`）使用同一份合成图谱、同一浏览器和同一采样窗口对比：

- 图谱重建：`7564.83 ms` 降至 `792.78 ms`，减少 `89.52%`，约 `9.54x` 加速。
- 单个完成渲染帧的 WebGL draw call：`8619` 降至 `104`，减少 `98.79%`，约 `82.88x` 降低。
- 单个完成渲染帧的顶点/索引处理量：`14163114` 降至约 `3727605`，减少 `73.68%`，约 `3.80x` 降低。
- 1.5 秒采样窗内：主干完成 `1` 帧，优化工作树完成 `3` 帧。由于主干没有完成第二帧，主干 FPS 不足以形成稳定平均值；不能把该窗口的 `0 FPS` 直接外推为真实设备最终 FPS。
- 两侧均无 console error 或 page error。

这说明当前工作树的主要项目收益已经从“代码结构优化”转化为可量化的交互余量：3000 节点级别的首次图谱构建时间从多秒降到约 1 秒内，单帧 GPU 提交压力显著下降，标签和拾取对象数量也不再随节点数线性增长到同等规模。

## 测试输入

严格采用需求中给出的节点数量：

| 类型 | 数量 |
| --- | ---: |
| Product / 配方 | 1000 |
| Ingredient / 成分 | 1458 |
| Evidence / 循证证据 | 319 |
| HealthTopic / 健康结局 | 94 |
| 合计 | 2871 |

关系共 `1413` 条：1000 条配方→成分含量关系、319 条成分→循证证据关系、94 条循证证据→健康结局关系。配方→成分关系使用 `1 mg` 到 `1000 mg` 的含量值，覆盖点击配方后按含量调节成分节点大小和颜色的路径。

## 采样方法

- 两个独立工作树：`origin/main` 和 `optimize/kg-viewer-3000`。
- 同一 `make dev` 启动方式，不复用进程和浏览器页面。
- Chromium headless，视口 `1440x1000`，device scale factor `1`。
- 通过页面 drop 事件加载同一份合成 JSON，等待页面统计文本确认 `2871 节点`。
- 重建时间从 drop 触发到统计文本出现。
- 重置计数器后采样 `1500 ms`，在 WebGL 层统计 draw call、实例化调用、顶点/索引参数以及 requestAnimationFrame 次数。
- 绝对值受当前机器的 headless 软件 WebGL 速度影响；分支间使用同一环境，故相对变化更有参考价值。

## 原始采样结果

| 指标 | `origin/main` | `optimize/kg-viewer-3000` | 变化 |
| --- | ---: | ---: | ---: |
| 图谱重建耗时 | 7564.83 ms | 792.78 ms | -89.52% |
| 采样窗内 draw call | 8619 | 312 | 不直接比较 |
| 完成渲染帧数 | 1 | 3 | +2 帧 |
| 每完成渲染帧 draw call | 8619 | 104 | -98.79% |
| 采样窗内顶点/索引处理量 | 14163114 | 11182815 | 不直接比较 |
| 每完成渲染帧顶点/索引处理量 | 14163114 | 3727605 | -73.68% |
| 实例化 draw call | 1 | 6 | 优化侧批量路径 |
| 页面错误 | 0 | 0 | 无回归 |

优化分支调试快照同时确认：`2871` 个节点、`1413` 条关系、`96` 个标签候选、`9` 个 geometry，节点和关系均走批量渲染路径。

## 额外压力回归

在之前的浏览器回归中，优化分支还用 `3071` 节点、`1613` 条关系完成了批量渲染、标签 LOD、配方含量视觉映射和 Escape 复位验证：无 console/page error，标签数保持 `96`，选择配方后目标成分的 scale/color 发生变化，复位后恢复原值。

## 解读边界

这份结果是“同机同浏览器的分支相对基准”，不是对所有用户设备的绝对 FPS 承诺。生产环境还应在一台真实 GPU 设备和一台低端设备上各跑一次同样脚本，并把首屏可交互时间、连续拖拽时的 p95 帧间隔纳入发布门槛。
