# KG Viewer 3000 节点实时 Neo4j 性能对比

## 结论

以当前远端主干 `origin/main`（`6a36da8`）为基线，和优化工作树 `optimize/kg-viewer-3000`（`e202613`）使用同一个实时 Neo4j v2-zh 数据源、同一浏览器和同一采样窗口对比：

- 两次复测平均从页面请求实时 API 到图谱进入可渲染状态：`6018.90 ms` 降至 `3084.23 ms`，减少 `48.76%`，约 `1.95x` 加速。
- 单个完成渲染帧的 WebGL draw call：`8619` 降至 `104`，减少 `98.79%`，约 `82.88x` 降低。
- 单个完成渲染帧的顶点/索引处理量：`14264954` 降至 `3829445`，减少 `73.15%`，约 `3.73x` 降低。
- 1.5 秒采样窗内两侧都完成 `1` 帧。实时图谱包含 `52333` 条关系，当前 headless 软件 WebGL 环境不足以形成稳定 FPS；不能把该窗口的 `0 FPS` 直接外推为真实设备最终 FPS。
- 两侧均无 console error 或 page error。

这说明当前工作树的主要项目收益已经从“代码结构优化”转化为可量化的交互余量：在真实 2871 节点、52333 关系的图谱上，页面可渲染时间平均降低约 49%，单帧 GPU 提交压力显著下降，标签和拾取对象数量也不再随节点数线性增长到同等规模。

## 测试输入

严格采用需求中给出的节点数量：

| 类型 | 数量 |
| --- | ---: |
| Product / 配方 | 1000 |
| Ingredient / 成分 | 1458 |
| Evidence / 循证证据 | 319 |
| HealthTopic / 健康结局 | 94 |
| 合计 | 2871 |

实时 API 返回 `52333` 条关系。两侧 API 均确认 `code=0`、`source=neo4j`，节点类型数量完全一致：Product 1000、Ingredient 1458、Evidence 319、HealthTopic 94。

## 采样方法

- 两个独立工作树：`origin/main` 和 `optimize/kg-viewer-3000`。
- 同一 `make dev` 启动方式，不复用进程和浏览器页面。
- Chromium headless，视口 `1440x1000`，device scale factor `1`。
- 页面直接请求同源 `/v1/graph/kg`，等待页面状态确认 `已从后端加载 2871 节点 / 52333 关系`。
- 可渲染时间从页面导航完成到统计文本确认。
- 重置计数器后采样 `1500 ms`，在 WebGL 层统计 draw call、实例化调用、顶点/索引参数以及 requestAnimationFrame 次数。
- 两侧均使用主干工作区的 `KG_GRAPH_PROFILE=v2-zh` 配置和同一 Neo4j v2 URI；不复制或记录密码。
- 绝对值受当前机器的 headless 软件 WebGL 速度影响；分支间使用同一环境，故相对变化更有参考价值。

## 原始采样结果

| 指标 | `origin/main` | `optimize/kg-viewer-3000` | 变化 |
| --- | ---: | ---: | ---: |
| 页面到可渲染状态 | 5707.21 ms | 3252.90 ms | -43.00% |
| 采样窗内 draw call | 8619 | 104 | -98.79% |
| 完成渲染帧数 | 1 | 1 | 持平，受实时关系密度限制 |
| 每完成渲染帧 draw call | 8619 | 104 | -98.79% |
| 采样窗内顶点/索引处理量 | 14264954 | 3829445 | -73.15% |
| 每完成渲染帧顶点/索引处理量 | 14264954 | 3829445 | -73.15% |
| 实例化 draw call | 1 | 2 | 优化侧批量路径 |
| 页面错误 | 0 | 0 | 无回归 |

上表的首项和采样计数来自第一次复测；第二次复测的页面到可渲染状态为主干 `6330.58 ms`、优化分支 `2915.55 ms`。两次复测平均值为主干 `6018.90 ms`、优化分支 `3084.23 ms`，即减少 `48.76%`、约 `1.95x` 加速。

优化分支调试快照同时确认：`2871` 个节点、`52333` 条关系、`96` 个标签候选、`9` 个 geometry，节点和关系均走批量渲染路径。

## 之前结果的修正

此前使用的 synthetic/drop 基准是在优化工作树没有加载 `.env` 时运行的，页面实际回退到内置 `676` 节点 snapshot；它只能验证批量渲染和 3000 节点压力路径，不能作为主干收益结论。本报告已改为实时 Neo4j API 对比，之前的 synthetic 结果不再用于收益计算。

## 额外压力回归

在之前的浏览器回归中，优化分支还用 `3071` 节点、`1613` 条关系完成了批量渲染、标签 LOD、配方含量视觉映射和 Escape 复位验证：无 console/page error，标签数保持 `96`，选择配方后目标成分的 scale/color 发生变化，复位后恢复原值。

## 解读边界

这份结果是“同机同浏览器的分支相对基准”，不是对所有用户设备的绝对 FPS 承诺。生产环境还应在一台真实 GPU 设备和一台低端设备上各跑一次同样脚本，并把首屏可交互时间、连续拖拽时的 p95 帧间隔纳入发布门槛。
